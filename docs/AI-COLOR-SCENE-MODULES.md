# 照片内容与光线提示词模块

日期：2026-09-23。本文与 [分层工作流](AI-COLOR-WORKFLOW-V2.md) 和 [阶段提示词](AI-COLOR-PROMPTS-V2.md)共同组成实施契约。这里的规则是调色时的关注点，需要用真实照片和当前渲染结果验证。

## 1. 模块解决的问题

同样一句“自然优化”，在人像上主要关心人物的亮度与肤色，在风景上还要看天空、地面和远近层次。照片也可能同时是“夜景 + 建筑 + 人物”。因此，照片内容与光线分别描述，允许组合。

内容标签描述画面中可见的主体。光线标签描述拍摄时的照明情况。风格目标由用户任务提供，不能根据内容标签擅自确定。比如“人像”不自动等于磨皮，“风景”不自动等于高饱和。

诊断 D 在已有的一次视觉调用中同时产出内容与光线分类。无需额外增加一次照片类型分类调用。D 使用第 2 节的短分类规则；得到结构化结果后，由程序挑选下面对应的模块。简单且明确的追问仍可直接进入 P，此时使用公共规则与任务模块；P 从当前图片做必要的局部判断，不启动完整分类流程。

## 2. 分类结构与选择规则

为 EditBrief 增加 `sceneProfile`。字段值由 Zod 枚举限定；未看到的内容不能添加。

```ts
// 这份数据只选择提示词模块，不授予编辑权限。
type SceneProfile = {
  subjects: Array<
    'person' | 'landscape' | 'architecture' |
    'food_product' | 'animal' | 'other'
  >; // 1–2 项，按这次任务的重要性排序
  lighting: Array<'night' | 'backlit' | 'mixed_light' | 'flat_hazy'>; // 0–2 项
  primarySubject: 'person' | 'landscape' | 'architecture' |
    'food_product' | 'animal' | 'other';
  subjectEvidence: string; // 当前图片中可见的依据，最多 100 字
  lightingEvidence: string | null; // 没有明确条件时为 null
  targetIds: string[]; // 已有区域 ID；可为空
};
```

`subjects[0]` 必须等于 primarySubject。含人物的小比例风景照可以标为 `['landscape','person']`；人物明显是用户目标时改为 `['person','landscape']`。`lighting` 是标签数组，不是互斥类；例如夜间混合灯光可同时使用 night 与 mixed_light。

分类依据以用户本次目标与照片可见内容为准。用户说“只修天空”，且画面有人物时，人物仍可进入 subjects，但对应的局部动作不能因此扩大到人物。看不清的主体写 other，并在 observations 记录不确定性。参考图的类别另作视觉观察，不用它替换待编辑照片的 sceneProfile。

同一张图的场景内容在当前会话中通常稳定，可按 imageId + sourceVersion 缓存 D 的可见内容判断；用户意图改变时重新决定 primarySubject 的任务排序。裁切改变使某个主体离开画面时，需要重新诊断可见主体。已有蒙版的标签不等于视觉分类证据。

## 3. 组合与优先级

一次 P 或 V 调用按以下顺序组装内容：

```text
公共规则 common
当前阶段 prompt
当前任务模块（只选一个主任务）
主体模块（最多两个，按任务重要性排序）
光线模块（最多两个）
真实能力卡与输出 Schema
当前阶段结构化输入和有角色的图片
```

公共规则和任务约束控制权限；模块提供要观察、保留和检查的视觉要点。用户明确意图决定编辑方向。主体与光线模块发生建议冲突时，优先保留用户提出的限制，再看主要主体与真实画面证据；无法兼顾时写入 D 的取舍或向用户澄清。模型不得因为模块提到某种参数，就输出未获授权的参数或局部能力。

组合最多两个主体、两个光线模块。对 `other` 不注入主体模块。模块中的内容只在该场景实际可见、与任务有关时使用；无需为了覆盖所有模块条目而调整照片。所有标签、模块 ID、版本和选择顺序写入工作流日志，便于比较效果。

例如“夜景里的人像，保留街灯暖色，让人物清楚一点”：

```text
common + P + natural + subject.person + lighting.night + lighting.mixed_light
```

如果用户明确说“只调人物”，在这个组合里还加入 P 的 `allowedTargetIds` 作用范围，并保持全局赋值为空。模块没有权力覆盖选区范围。

## 4. 主体模块

### subject.person-v1：人像与人物

```text
优先观察人物面部和身体的明暗可读性、肤色与现场光源的关系、人物与背景的分离程度。
保留不同肤色的固有差异、场景暖冷光和人物衣物的真实色彩。
人物清楚不要求皮肤更白；需要提亮时关注高光、额头与浅色衣服是否过亮。
降噪或降低清晰度时检查眼睛、头发、皮肤与衣服纹理，避免无依据地抹平细节。
多人画面需用明确选区 ID 或用户指认决定目标；任务没有提到的人物保持原状。
```

### subject.landscape-v1：自然风景

```text
优先观察天空与地面的亮度关系、远近层次、水与植被的颜色关系，以及主要景物的可读性。
保留天气、时间和空气透视带来的气氛；薄雾、阴天或逆光可能是照片主题。
提升层次时检查天空是否变脏、云层是否被压成灰块，植被与水面是否过饱和。
太阳附近、雪地和水面反光不要求完全有纹理；已丢失细节不得声称恢复。
景深与远处雾感需要保持时，去雾只能在用户目标允许的程度使用。
```

### subject.architecture-v1：建筑与城市

```text
优先观察建筑立面、窗户、天空及阴影的层次，保留材质和人工灯光的真实颜色。
白墙和灰色材质可帮助检查明显偏色，但不能假设所有墙面应为中性白。
提亮立面时检查窗外与室内灯是否失去层次；压暗天空时检查建筑边缘的可见过渡。
强对比可突出结构，也可能吞掉立面纹理；根据用户想表达的氛围决定强度。
本任务若未授权构图，不改变倾斜、透视或画幅；当前参数也无法进行透视校正。
```

### subject.food_product-v1：食物与商品

```text
优先观察主体固有颜色、表面质感、反光与背景对主体的干扰。
保持用户希望呈现的真实色彩；“更诱人”或“更干净”不能自动变成大幅提高饱和度。
关注白盘、包装、金属或玻璃上的高光，防止变成无层次的亮块。
背景需要安静时优先考虑已允许的局部选区调整，保持产品细节和品牌色。
若商品颜色真实性对用户重要，给出保守建议并让用户确认实际颜色。
```

### subject.animal-v1：宠物与动物

```text
优先观察眼部可读性、毛发或羽毛细节、主体与背景的分离。
保留毛色、羽色与现场光线的关系；提升主体不等于提高整张图曝光。
降噪或降低清晰度时检查细毛、胡须和羽毛边缘；粗糙背景允许另行局部处理。
无法从缩略图判断细节时请求真实像素局部图，并标记不确定性。
```

## 5. 光线模块

### lighting.night-v1：夜景与低照度

```text
保留夜晚的暗部基调和灯光颜色，检查主体是否仍可辨认。
提亮阴影时关注颗粒和颜色杂点；不要把整个夜景提成均匀的白天亮度。
灯牌、车灯和窗口允许明亮，检查其周围层次是否被不必要地裁切。
降噪前看真实像素局部图，区别噪点、雨雪、细节和有意的颗粒效果。
```

### lighting.backlit-v1：逆光

```text
关注主体与高亮背景之间的亮度差、轮廓光和发光氛围。
若用户希望主体更清楚，优先判断有无可用的主体蒙版；全局提亮可能使背景更亮。
边缘过渡与发丝处容易出现不自然调整，视觉检查需要看对应区域。
保持太阳、窗户等光源的视觉亮度，不承诺恢复已纯白区域的纹理。
```

### lighting.mixed_light-v1：混合光源

```text
识别画面中可能并存的暖灯、窗光、霓虹等色彩关系。
全局色温或色调只能整体作用；不要求所有光源同时呈中性色。
保留用户想要的主光氛围，检查人物肤色、白墙和背景是否出现明显冲突。
用户要求只修一处偏色且当前缺少局部白平衡能力时，说明功能范围，不扩大成全局改色。
```

### lighting.flat_hazy-v1：低反差、阴天或雾感

```text
观察低反差源于天气、空气雾气、逆光还是用户已经形成的风格。
需要增强层次时，从主体可读性和近远关系出发，避免整张图同时变硬。
去雾会改变颜色和亮度；候选渲染后检查天空、植被与物体边缘。
用户要求保留柔和气氛时，把保留空气感写入成功条件。
```

## 6. 与各阶段的关系

| 阶段 | 使用方式 |
| --- | --- |
| R 路由 | 只判断任务路线与作用范围；通常不读取主体模块 |
| D 诊断 | 使用第 2 节短分类规则，生成 SceneProfile；观察可见画面并决定目标 |
| T 目标准备 | 只使用 D 的目标清单与用户点选，SAM 不接收调色主体模块 |
| P 规划 | 按程序选中的模块提醒观察重点与保留项；参数范围仍由能力卡决定 |
| V 视觉检查 | 使用同一 SceneProfile 与模块检查原目标是否达成、是否伤害保留项 |
| C 修正 | 只注入与检查问题相关的模块，遵守 allowedParameterNames |

模块中“优先观察”是检查顺序，不等于必须增加某项参数。D 的用户目标与 V 的实际结果对最终建议有决定作用。

## 7. 组合样例与期望行为

| 照片与请求 | 组合 | 期望关注点 |
| --- | --- | --- |
| 暖灯室内人像，“自然一点” | person + mixed_light + natural | 让人物清楚，同时保留暖灯氛围 |
| 阴天山景，“更有层次” | landscape + flat_hazy + natural | 检查远近与天空，避免全面强去雾 |
| 夜晚建筑，“保留霓虹但看清立面” | architecture + night + mixed_light + natural | 灯光颜色与立面可读性分别检查 |
| 逆光海边情侣，“只提亮两个人” | person + landscape + backlit + local | 两人选区内提亮，区域外保留夕阳 |
| 商品玻璃杯，“白背景更干净” | food_product + natural | 检查白色与玻璃高光，同时保持商品色 |
| 室内宠物，“降低噪点” | animal + mixed_light + restoration | 真实像素检查毛发与颜色杂点 |
| 人像照，“只调整我选中的红衣服” | person + local | 用户选区决定作用范围，肤色保持 |
| 夜景参考图配日间城市照 | architecture + reference | 提取可实现的冷暖与层次，保留本图光线逻辑 |

以上样例验证路由和保留项，不能证明最终数值正确。最终仍按真实照片评测主观偏好和修正成本。

## 8. 实施与验收

1. 在共享契约中增加 SceneProfile Schema，与 EditBrief 一起返回；不新增独立分类 API。
2. 实现允许列表映射：标签 → 模块 ID/版本，最多两个主体和两个光线模块；未知标签由 Schema 拒绝。
3. 公共提示词、阶段模板、任务片段、主体片段和光线片段使用独立文件。输出 Schema 保持从领域与 AI 契约生成。
4. 把本轮选择的 sceneProfile、模块 ID 及版本加入工作流记录。客户端可以显示简短关注点，避免展示原始提示词。
5. 在至少 40 张真实照片的评测集中覆盖混合主体、混合光、用户意图与类型默认方向冲突的样本。比较加入模块前后的用户偏好、失败样本与模型调用耗时。

验收时需确认：相同用户请求在人像与风景照上的建议重点有合理差异；混合场景允许两个主体；没有任何类型模块越过用户明确指定的作用范围或操作权限；模型未见的物体不被编造。
